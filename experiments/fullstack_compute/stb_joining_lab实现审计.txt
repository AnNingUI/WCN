stb_joining_lab 实现审计

一、审计对象
- 目标：评估在“不依赖 HarfBuzz”的前提下，为 stb 后端补充 Arabic joining 能力的可行性与成本。
- 范围：仅针对实验室验证，不直接改主线 impl/ 与渲染路径。

二、已确认事实
1. 当前构建未开启 FS_HAS_HARFBUZZ。
   - 现状：Arabic 可以显示、RTL/右对齐可工作，但不会真正连写。
2. freetype2 backend 代码中存在 HarfBuzz shaping 路径，但当前编译产物未启用。
3. stb_truetype 的定位更接近“轻量字形栅格器”，不是完整复杂文本引擎。
4. 当前 stb backend 已保留字体原始 bytes，这对实验是有利条件。
5. 之前 CBDT 路线已经证明：围绕 stb 增加字体能力扩展是可行的，但 Arabic joining 的难度高于 CBDT。

三、评估目标
本实验只回答以下问题：
1. 是否存在至少一个字体，能让 stb-only Arabic joining 走“规则驱动 + 可利用 form glyph”的路线。
2. 这种路线是否只需有限规则即可做出明显优于“孤立字形”的效果。
3. 如果字体层面不成立，是否意味着必须进入 GSUB/OpenType 解析，导致成本显著上升。
4. 最终结论是：值得继续 / 只适合实验 / 不值得继续。

四、明确边界（非目标）
- 不依赖 HarfBuzz。
- 不改主线 backend。
- 不处理多字体 fallback。
- 不做自动换行。
- 不做完整 bidi 引擎。
- 不做 GPOS/mark positioning。
- 不做 Indic/Thai/Hebrew 等其他复杂脚本。
- 不追求 freetype2 + HarfBuzz 等级的完整质量。

五、实验范围定义
- Arabic only。
- 单字体。
- 单段文本。
- 先做字体可行性评估，再决定是否进入 joining PoC。
- 目标是“demo/lab 级 joining 可行性”，不是主线级文本引擎。

六、实施阶段清单

Phase 0：边界锁定
[ ] 目标限定为 Arabic only
[ ] 明确不依赖 HarfBuzz
[ ] 明确不改主线 impl/
[ ] 明确单字体实验
[ ] 明确先评估字体可行性，再决定是否做 joining PoC

Phase 1：Lab 骨架
[ ] 在 experiments/ 下建立 stb_joining_lab
[ ] 结构沿用 stb_color_font_lab 的风格
[ ] 准备最小 CLI：输入字体文件 + 测试模式，输出终端报告 + 可选 dump
建议结构：
[ ] experiments/stb_joining_lab/CMakeLists.txt
[ ] experiments/stb_joining_lab/src/main.c
[ ] experiments/stb_joining_lab/output/

Phase 2：候选字体收集
[ ] 收集 Windows 本机 Arabic-capable 字体候选
[ ] 收集实验专用 Arabic 字体候选（如系统字体不理想）
[ ] 每个字体记录：文件名 / 格式（TTF/TTC）/ face index / stb 是否可加载
输出：字体矩阵表

Phase 3：最小测试字符集
A. 基础 Arabic 字母
[ ] 选一组可双向连接字母
[ ] 选一组只接前不接后的边界字母
B. Presentation Forms
[ ] isolated
[ ] initial
[ ] medial
[ ] final
C. 最小真实样本文本
[ ] 1 条 Arabic 单词
[ ] 1 条 Arabic 短句
[ ] 1 条 Arabic + Latin 混排样本（仅观察，不作为首轮成功标准）

Phase 4：字体可行性探针
[ ] 检查基础 Arabic codepoint 是否存在 glyph
[ ] 检查 Presentation Forms codepoint 是否存在 glyph
[ ] 检查同一字母不同 form 是否映射到不同 glyph index
[ ] 检查 stb 是否能按这些 glyph index 正常拿到 bitmap/metrics
输出：每个字体一份 dump + 汇总表

Phase 5：字体可利用性评级
[ ] 高可用：基础 Arabic + forms 都可用，且 form glyph 差异明确
[ ] 中可用：部分 forms 可用，demo 可能成立但质量不稳
[ ] 低可用：只能显示基础字母，form 基本不可区分
输出：font_feasibility_report

Phase 6：决策门
Gate A（继续）
[ ] 至少一个字体被评为高可用或中可用偏高
=> 进入 Phase 7：规则驱动 joining PoC

Gate B（止损）
[ ] 候选字体全部低可用，或 form 不可区分
=> 结论：stb-only Arabic joining 很可能必须进入 GSUB/OpenType 解析，成本升级，不建议直接继续

Phase 7：规则驱动 joining PoC（仅在 Gate A 后执行）
范围：单字体 / Arabic only / 单段文本 / 不做通用 bidi / 不做 GPOS
[ ] 实现最小 joining class 判断
[ ] 根据前后连接关系决定 isolated / initial / medial / final
[ ] 将结果映射到对应 form codepoint 或 glyph
[ ] 用 stb 栅格化输出结果图
[ ] 与“孤立字版本”做视觉对比

Phase 8：最终结论
[ ] 值得继续：规则驱动路线对 Arabic 有现实价值
[ ] 只适合实验：demo 可行，但不建议主线化
[ ] 不值得继续：必须进入 GSUB/OpenType 解析，成本过高
输出：SUMMARY 与后续建议

七、成功标准
满足任一即可视为实验成功：
1. 找到至少一个字体，证明 stb-only Arabic joining 存在现实基础。
2. 明确证明：若无字体基础，则继续会直接进入 GSUB/OpenType 解析成本区。

八、止损标准
出现任一情况即可停止继续投入：
1. 候选字体几乎都不暴露可利用的 Arabic form glyph。
2. 不同 form 实际不能稳定区分。
3. 想得到正确结果必须直接进入 GSUB 解析。

九、当前审计结论（阶段性）
- 这条路线不是常规路线，但做 Lab 有价值。
- 先做“字体可行性优先”是正确策略。
- 若字体可利用性不足，则 stb-only Arabic joining 很可能会从“规则实验”迅速升级成“自研小型 shaping engine”问题。
- 建议先做到 Phase 5，再决定是否值得进入 Phase 7。
