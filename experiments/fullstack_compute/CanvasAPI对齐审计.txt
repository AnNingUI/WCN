2.2 fs_path_fill GPU-only 失败路径（队友 api-path 修订）

k.md 声明：GPU clip 失败时返回 false，无 CPU 恢复路径。
k.md 原文："fs_path_fill is now strict GPU-only: SDF-based clip-mask solve in clip compute for edge AA." / "if GPU clip path creation fails, fs_path_fill now returns false (no CPU recovery path)."

实际代码：fullstack_core.c:7018-7147+ 有完整 CPU 三角化 fallback 路径。
k.md 比代码更严格；实际实现更健壮：
  - 第 7030-7034 行：先尝试 GPU clip-mask job
  - 第 7036 行起：GPU 失败后执行 CPU 三角扇区化回退

fs_clip_path 执行路径也比 k.md 描述更复杂：
  - axis-aligned rect fast-path (c:5927)
  - axis-aligned roundRect fast-path (c:5946)
  - GPU clip compute → AABB fallback (c:5903)

对齐结论：k.md 描述偏严格；代码更健壮。两者差异不影响用户 API 行为（GPU 路径优先，失败时 CPU 透明回退）。

五、Pixel IO / Context / Image API 对齐（api-pixel 负责）

5.1 getImageData — readback 时机

Canvas 2D 规范：getImageData(sx, sy, sw, sh) 返回指定区域的当前 canvas 数据，
  读取发生在"立即调用时"（same-call semantics）。

k.md 声明：readback 源是"最近一次提交/呈现的帧 copy"，不是 full browser same-call immediate parity。
状态：已确认。
  - fs_encode_canvas_readback_copy (fullstack_core_canvas.c:150) 复制 target_texture 全帧
  - fs_core_get_canvas_image_data_rgba8 (fullstack_core.h:455) 先尝试从 readback buffer 刷新，
    失败后回退到 canvas shadow
  - readback 时机：在 fs_core_encode 末尾，滤镜链之后/presentation pass 之后
  - 如果 filter chain 修改了 scene_texture，readback 得到的是 presentation 后的内容
对齐差距：MEDIUM — 无法读取 filter 链中间状态；格式固定为 RGBA8；BGRA 处理路径存在但精度有限。
k.md 描述准确。

5.2 putImageData / createImageData

Canvas 2D 规范：
  - createImageData(width, height) → 返回 zero-initialized ImageData 对象
  - putImageData(imageData, dx, dy) → 绘制到 canvas
  - putImageData(imageData, dx, dy, dirtyX, dirtyY, dirtyW, dirtyH) → dirty rect 版本

当前状态：
  - fs_core_create_image_data_rgba8 (fullstack_core.h:438) 存在，但返回 bool 而非 ImageData 对象
    实现：分配 zero-initialized RGBA8 缓冲区，通过 out_rgba_pixels / out_rgba_size 返回
    语义差异：Canvas API createImageData 返回 ImageData 对象（有 width/height/data 属性）
              fullstack_compute 版本是纯输出缓冲区创建
  - fs_core_put_canvas_image_data_rgba8 (fullstack_core.h:445) 存在，但只有 (dst_x, dst_y, width, height) 版本
    缺少 dirty rect 重载（sx, sy, sw, sh 参数）
  - k.md:272 未明确提到 createImageData 的对象语义差异和 putImageData dirty rect 缺失

对齐差距：MEDIUM — createImageData 语义不同（无 ImageData 对象）；putImageData 缺少 dirty rect 重载。

5.3 canvas.toDataURL / canvas.toBlob

Canvas 2D 规范：canvas.toDataURL(type, encoderOptions) 和 canvas.toBlob(callback, type, encoderOptions)
是 Canvas 2D 的标准导出 API。

当前状态：完全缺失。
  grep 搜索结果：无 toDataURL / toBlob 相关实现（src/ 目录下零匹配）
  k.md 未标注此项

对齐差距：HIGH — 导出 API 缺失，k.md 未标注。

5.4 context_lost 恢复

Canvas 2D 规范：contextlost 事件触发后可尝试 context.reset() 并重新配置。

k.md 声明："NOT implemented yet: full browser-parity context loss recovery lifecycle and event model"。
状态：已确认。
  - fs_core_is_context_lost (fullstack_core.h:197) 存在
  - fs_core_get_context_attributes (fullstack_core.h:198) 返回固定后端能力

## 更正 1：fs_path_fill 不是纯 GPU-only，有 CPU 三角化回退

队友 api-path 审计发现：k.md:29-33 声明 fs_path_fill strict GPU-only no CPU recovery path，
但实际代码 fullstack_core.c:7018-7147 有完整 CPU 三角扇区化回退路径（GPU 失败后透明回退到 CPU）。
fs_clip_path 也有 axis-aligned rect fast-path、roundRect fast-path、GPU compute、AABB fallback 等多路径。
结论：k.md 描述偏严格；代码实现更健壮。

## 更正 2：drawImage 规范只有 3 种签名，不是 9 种

队友 api-text 核实：Canvas 2D 规范实际定义了 3 种 drawImage 签名：
  1. drawImage(img, dx, dy)
  2. drawImage(img, dx, dy, dw, dh)
  3. drawImage(img, sx, sy, sw, sh, dx, dy, dw, dh)
公共 API 有 fs_cmd_image (9 参数) 和 fs_cmd_image_handle (5 参数) 两个相关函数。
k.md 未声明 drawImage，不算文档错误（k.md 无此项声明）。
