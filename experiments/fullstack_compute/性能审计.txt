执行摘要

本报告聚焦 fullstack_compute 项目中经代码级验证的性能热点与可优化点，按影响
与优化难度分 P0~P3 四级。

最需要立即处理的性能问题：
  1. 滤镜链全画布后处理 — 无 dirty-rect/ROI 边界，每个滤镜都跑全图
  2. clip_job 每帧多次堆分配 — 验证过滤后重新分配 valid_jobs/xforms 缓冲区
  3. blur kernel 每次上传无缓存 — 相同半径跨帧重复生成并 QueueWrite
  4. 点操作滤镜无融合 — 8 种逐像素滤镜各自触发独立 compute pass
  5. canvas readback 固定 8 次 poll — 高负载下同步等待或静默超时

一、当前 Live 高影响性能问题

P-01 [HIGH] 滤镜链全画布后处理 — 无 dirty-rect / ROI 优化
文件: src/fullstack_core.c:4420-4424, src/fullstack_filters.c:557-789
根因: 渲染先落 scene_texture，然后 `fs_filter_chain_execute()` 先整图 copy 到
       ping-pong A，对全图画布执行每个 filter 的 compute dispatch（blur 为 H+V
       两次，drop-shadow 额外 compute composite + 多次 copy），最后 copy 回
       scene_texture 再 presentation pass。即使滤镜只影响画面一小块区域，
       也跑全画布多次。
影响: 画布面积线性决定后处理带宽，4K 画布下滤镜成本急剧放大。
优化方向: 以 filter bounds（blur 按 radius / shadow offset 外扩）为 dirty rect，
         只对 ROI 区域分配临时纹理和 dispatch，覆盖 core->width/height
         的 tile 工作而非全屏 pass。

P-02 [HIGH] clip_job 每帧多次堆分配
文件: src/fullstack_core.c:3911-3930, 4017-4041
根因: `fs_execute_clip_jobs()` 在验证 job 有效性后，对有效 job 重新分配
       valid_jobs / valid_xforms / valid_bucket_ids 三个堆缓冲区（共 3 次
       malloc），在排序重组后再各分配 ordered_jobs / ordered_xforms
       两个 calloc（共 2 次），随后立即 free（共 5 次）。即每帧 clip
       活跃时至少 5 次堆操作。
影响: 频繁 malloc/free 触发碎片化、TLB 抖动和帧抖动；中大型裁剪场景尤其明显。
优化方向: 预分配 ordered_jobs / ordered_xforms 缓冲区并按 max_bucket_size
         固定复用，仅在容量不足时grow；valid_* 缓冲区用栈上 small-array
         或 frame-local 池。

P-03 [HIGH] blur kernel 每次上传无缓存
文件: src/fullstack_filters.c:582-594, src/fullstack_effects.c:920-934
根因: 每遇到一个 blur 节点都执行 `fs_gaussian_kernel_compute_for_blur()` 并
       两次 `wgpuQueueWriteBuffer()`（uniform + kernel weights）。同一半径
       跨帧/跨节点没有缓存。相比 physical shadow 路径已有 `current_kernel
       + kernel_dirty` 雏形，filter 链执行路径没有复用此机制。
影响: CPU 生成 kernel 的 float 计算成本 + driver 两次 buffer 提交在大量小 blur
       或重复样式场景被放大。
优化方向: 按 radius/kernel_size/sigma 做 kernel cache map，仅参数变化时
         重新生成和上传；常用半径预生成并常驻 GPU。

P-04 [HIGH] 点操作滤镜无融合
文件: src/fullstack_filters.c:719-756, src/fullstack_shaders.h:1662-1681
根因: brightness、contrast、grayscale、hue-rotate、invert、opacity、saturate、
       sepia 这 8 种逐像素代数变换每个节点都触发独立 compute pass，逐像素
       switch-case（filter shader:1669-1678）决定执行哪个。重复读写整图，
       内存带宽受限。
影响: 多个点操作滤镜叠加时 pass 数线性增长，GPU 端大量重复整图带宽。
优化方向: CPU 侧预折叠连续点操作为统一颜色矩阵/向量；或单 pass shader
         接收所有参数一次计算；将 switch-case 展开为单次 math 表达式。

P-05 [HIGH] canvas readback 固定 8 次 poll 同步等待
文件: src/fullstack_core_canvas.c:76-88
根因: `wgpuBufferMapAsync` 后用固定 8 次 `wgpuDevicePoll(core->device,
       true, NULL)` 等待，map_ctx.done / map_ctx.success 标志共享无原子语义。
       高负载时 8 次 poll 可能仍然不够，map_ctx.done == 0 返回 false 导致
       readback 静默失败。
影响: 读回帧丢失、同步 stall、帧时间抖动。
优化方向: 改为 event/wakeup 语义（WaitAny / OnSubmittedWorkDone）或增加
         poll 次数上界；实现 map 成功/失败回调直接更新 serial。

P-06 [HIGH] per-frame 全量 command + state buffer 上传
文件: src/fullstack_core.c:4297-4321
根因: `fs_core_encode()` 每帧无条件执行两次 `wgpuQueueWriteBuffer`
       分别上传 command 和 command_states 完整数组，即使实际 command_count
       不变（场景相同）也要重新提交全部数据。
影响: CPU 侧 memcpy + driver submit 成本随 command 数线性增长；无 dirty-range
       跟踪导致 GPU 重复接收相同数据。
优化方向: 引入 dirty-range 跟踪，仅在命令内容实际变化时上传；或按
         command_count 变化率分档处理（小变化走小 buffer patch）。

二、当前 Live 中影响性能问题

P-07 [MEDIUM] clip bucket 每次按 frame 动态创建 bind group
文件: src/fullstack_core.c:4129-4148, 4190-4203, src/fullstack_core_clip_resources.c:32-108
根因: edge_transform pass 和 clip pass 的每个 bucket（最多 6 个）每帧都调用
       `fs_create_clip_edge_transform_bind_group_range()` /
       `fs_create_clip_compute_bind_group_range()`，返回后立即
       `wgpuBindGroupRelease()`。GPU 对象在热路径被创建/销毁。
影响: 驱动层对象管理开销、内存碎片、GPU 对象句柄泄漏风险（若某帧失败）。
优化方向: 预分配 6 个 bucket 对应的 bind group 并常驻复用；仅在 job
         内容/偏移变化时重建。

P-08 [MEDIUM] drop-shadow 执行时热路径创建 texture view
文件: src/fullstack_filters.c:661-695
根因: drop-shadow 节点执行时临时 `wgpuTextureCreateView()` 三次
       （shadow_tex / original_tex / dst_tex）和 `wgpuDeviceCreateBindGroup()`
       一次，pass 结束后立即 release。A/B ping-pong 和 shadow_composite_texture
       都是持久资源，但每次都要重新创建视图。
影响: 驱动层对象创建/释放成本在高频 drop-shadow 场景被放大。
优化方向: 预创建并缓存固定纹理视图组合（如 A→B→dst、B→A→dst 两套）；
         热路径只更新 uniform buffer 并直接复用。

P-09 [MEDIUM] gaussian blur shader 朴素 textureLoad 循环
文件: src/fullstack_shaders.h:1601-1629
根因: blur H/V pass 每像素循环执行 kernel_size 次 textureLoad，
       最大 63×2 = 126 次纹理采样/像素。无利用 GPU 纹理硬件采样器
       （sampler + texelFetch / textureGather）做优化。
影响: 纹理缓存未命中率高，片段着色器占用高，大半径 blur 帧时间显著退化。
优化方向: 改用 texelLoad + 预累加方式减少 sampler 压力；或利用 9-tap
         gaussian approximation 等快速近似；或 downsample-pyramid 多级方案。

P-10 [MEDIUM] blur dispatch workgroup size 次优
文件: src/fullstack_shaders.h:1601, 1616
根因: gaussian_blur_h 用 `@workgroup_size(256,1,1)`，gaussian_blur_v 用
       `@workgroup_size(1,256,1)`。对 2D 纹理问题用 1D workgroup 严重
       浪费 GPU 调度槽。
影响: GPU 占用率低，延迟增加。
优化方向: 改用 `@workgroup_size(16,16,1)` 或类似 2D tile；根据设备
         `maxWorkgroupSize` 上限选择最优 tile 大小。

P-11 [MEDIUM] drop-shadow compute shader offset 无边界保护
文件: src/fullstack_shaders.h:1776-1777
根因: `textureLoad(shadow_tex, vec2<i32>(c) - off, 0)` 对 offset 未做
       clamp。当 offset 超出纹理范围时在部分 GPU 上产生未定义行为，
       可能触发 WebGPU validation error。
影响: 负 offset drop-shadow（shadow 向左/上偏移）存在 GPU 越界读取风险。
优化方向: 在 shader 内部对 `c - off` 做 clamp 到纹理尺寸，或在 uniform
         阶段预 clamp offset。

P-12 [MEDIUM] font fallback 逐字线性扫描
文件: src/fullstack_core_text_glyph.c:603-613
根因: 字形未命中时对最多 FS_MAX_FONT_FALLBACKS=16 个字体做线性扫描
       依次 get_glyph_sdf，直到命中或全部失败。
影响: 罕见字/未收录字形触发 16 次字体查找，在中文字/符号密集文本中
       帧时间退化明显。
优化方向: 字体索引按覆盖范围预排序；或用 codepoint → font map 缓存
         跳过已知不包含该 codepoint 的字体。

P-13 [MEDIUM] glyph cache invalidation 触发全量 compaction + rebuild
文件: src/fullstack_core_text_glyph.c:459-479
根因: `fs_invalidate_cached_glyph()` 每次触发 O(n) memmove 数组压缩，
       随后立即 `fs_glyph_cache_rebuild()` 做 O(n) 哈希重建。
影响: 频繁纹理 atlas 换页或字体切换时，文字提交卡顿。
优化方向: 改用 tombstone 标记（lazy rebuild）；或原子更新哈希 slot，
         避免全量 compaction。

P-14 [MEDIUM] per-glyph atlas upload 逐张 memcpy + memset 填充
文件: src/fullstack_core_upload.c:122-127
根因: `fs_queue_write_texture_2d()` 对每张图像上行做逐行 memcpy +
       对 padded_row > tight_row 部分 memset 0。每帧多图上传时
       重复遍历相同行。
影响: 高频 draw_image 场景下 CPU memcpy 成本明显。
优化方向: 使用 SIMD memcpy；或使用 staging buffer 直接映射避免逐行填充。

三、Shader 与 GPU 效率问题

S-01 [HIGH] filter shader switch-case 分支分歧
文件: src/fullstack_shaders.h:1669-1678
根因: 8 种滤镜类型在单 shader 内用 switch-case 逐像素分发，GPU 线程
       执行相同路径但只有一条分支实际工作。
影响: shader 占用率低，分支分歧增加指令调度开销。
优化方向: 将各 filter 参数预折叠为统一 uniform 向量，单次 math 执行
         代替分支；或拆分为独立 shader variant。

S-02 [MEDIUM] 渲染 pass 布局 — 全屏绘制三角形 vs 顶点 buffer
文件: src/fullstack_core.c:4386, 4409-4412, src/fullstack_effects.c:1001-1003
根因: 渲染用 vertex buffer（vertex_count * 6）但 effects 全屏用
       覆盖三角形（@builtin(vertex_index) 推导）。两套路径不统一。
影响: 无实质性能差异，但增加 shader 维护成本。
备注: 这属于代码整洁性问题，非紧急性能项。

S-03 [MEDIUM] 无 GPU pipeline 状态缓存
文件: src/fullstack_core.c:4390-4393
根因: 渲染循环内对每个 command 批次查 pipeline 索引并 setPipeline，
       若 pipeline_index 未变化仍重复调用。
影响: 不必要的 API 调用。
优化方向: 在循环前缓存当前 pipeline，当前索引变化时才调 setPipeline。

四、构建与基准设施问题

B-01 [HIGH] 三个 demo 目标共享完整源码集 — 重复编译成本
文件: CMakeLists.txt:36-211
根因: fullstack_compute_demo、fs_text_layout_demo、clay_layout_demo
       三个 target 都显式列出了相同的 20+ 个源文件。
       改动任意一个核心源文件后需要编译 3 次才能验证全场景。
影响: 开发迭代速度下降，CI 构建时间线性增长。
优化方向: 将核心源文件集提取为 STATIC 库（fullstack_core_lib），
         三个 demo 只 link 该库。

B-02 [HIGH] 基准测试未集成 CMake
文件: Task/benchmarks/run_glfw_bench.ps1:17-21, Task/benchmarks/README.md
根因: 基准脚本硬编码 3 个 exe 路径（.\build\examples\GLFW\*.exe），
       但 CMake 并未将 benchmark 测试加入 build 目标。
       需要手动构建后再跑脚本，无法用 cmake --build --target benchmark。
影响: 每次代码修改后需要手动两步走才能验证性能。
优化方向: 在 CMakeLists.txt 中添加 benchmark 相关 target；或在
         run_glfw_bench.ps1 中自动触发 cmake --build。

B-03 [MEDIUM] 基准缺少 filter/effects 工作负载
文件: Task/benchmarks/run_glfw_bench.ps1:17-21
根因: 当前只有 path（line_cap_join）、text（sdf_text）、image
       三个场景，缺少 filter 密集工作负载（如 blur 链、drop-shadow
       组合、color-filter 叠加）的基准场景。
影响: filter 系统性能回归无法被基准发现。
优化方向: 添加 blur_stress_test、filter_chain_test 等专用场景。

B-04 [MEDIUM] 基准无 GPU timestamp 验证
文件: Task/benchmarks/run_glfw_bench.ps1:147-155
根因: 脚本接收 gpu_compute_ticks / gpu_render_ticks 字段，
       但代码中未见 WebGPU timestamp query 实际开启逻辑。
       `gpu_timestamp_samples` 可能始终为 null。
影响: 基准数据缺少 GPU 端精确热力图，无法定位 shader 热点。
优化方向: 在 demo 中启用 WebGPU timestamp query（需 WebGPU features
         支持），将 GPU time 纳入基准输出。

B-05 [MEDIUM] 无 CPU 端帧内计数器
文件: Task/benchmarks/run_glfw_bench.ps1:139-156
根因: 基准依赖 stdout WCN_STATS 解析，但未在核心代码中埋入足够细粒度
       的性能计数器（如 per-pass dispatch 数、texture copy 字节、
       per-batch draw call 数等）。
影响: 基准数据粒度粗，过度依赖 wall-clock 难以定位瓶颈。
优化方向: 在 fs_core_encode 等热路径增加原子计数器，按帧导出到 WCN_STATS。

B-06 [MEDIUM] 无 release 构建基准
文件: Task/benchmarks/run_glfw_bench.ps1:1-250
根因: 所有基准跑 Debug 或默认构建，未与 Release 构建对比。
       Debug vs Release 的帧时间差异在 C + WebGPU 场景可能超过 2x。
影响: 性能数字无法反映生产部署实际表现。
优化方向: 添加 Release 构建基准目标，配置 CMAKE_BUILD_TYPE=Release
         并记录在基准结果中。

五、已部分缓解的性能问题（来自 Task 任务追踪）

以下 Task 已实施但可能存在残留问题或改进空间：

T001 (bind group cache) — 纹理绑定组每帧复用
状态: 已验收，但 effects 子系统内仍有 per-execution bind group 创建
       （P-07, P-08），主渲染路径的改善未传导到 effects 路径。
残留: drop-shadow、filter_copy 等 effects 热路径仍在每帧创建/销毁。

T002 (render pass 合并) — 减少 per-batch render pass 碎片化
状态: 已验收，主渲染 pass 已合并，effects 和 presentation 仍有独立 pass。
残留: filter 链每节点独立 compute pass（P-04）。

T003 (glyph cache hash 索引) — 线性扫描 O(n) → hash 查找
状态: 已验收，但 invalidation 触发全量 compaction + rebuild（P-13）。
残留: 动态场景下仍是 O(n)。

T004 (path fill triangulation) — O(n^3) ear clip 存在 guard
状态: 已验收，guard_max = count*count*2u 上限存在，但大复杂多边形
       仍然触发 O(n^2) 每轮 O(n) = O(n^3) 最坏情况（P-11 related）。
残留: 最坏情况 DoS 仍可能。

T005 (stroke join 分配) — round join 动态分配已移除
状态: 已验收，代码中未见 per-join malloc。
无残留。

T006 (dirty-range instance upload) — 实例上传 dirty range 跟踪
状态: 已部分实施，command/state buffer 仍为全量上传（P-06）。
残留: uniform/command 上传未做 dirty tracking。

T007 (benchmark harness) — 基准框架已建立
状态: 已验收，但 filter 工作负载、GPU timestamp、Release 构建均未覆盖
       （B-02 ~ B-06）。

T009 (GPU round join commandization) — GPU 圆形填充替代 CPU 三角剖分
状态: 已实施，默认关闭（帧时间回退）。实验结论已记录。
无残留。

六、性能优化优先级总表

P0（立即实施 — 最大 ROI）
  1. P-01 滤镜链 dirty-rect / ROI 优化 — 全画布后处理是最大带宽瓶颈
  2. P-03 blur kernel cache — 消除每帧重复 CPU 生成 + 两次 QueueWrite
  3. P-04 点操作滤镜融合 — 8 种滤镜各自独立 pass 是明显的 pass 数膨胀
  4. P-02 clip_job 帧内堆分配消除 — 5 次 malloc/free 触发了即释放

P1（下一迭代 — 中高 ROI）
  5. P-06 command/state dirty-range 上传 — 全量每帧上传浪费 CPU+GPU 带宽
  6. P-07 clip bucket bind group 缓存 — 6 个 bucket 每帧重建释放
  7. P-05 canvas readback 同步改进 — 固定 poll 次數不足时静默失败
  8. P-08 drop-shadow texture view 缓存 — 热路径对象 churn
  9. P-12 font fallback 线性扫描优化 — 16 字体内 O(n) 扫描
 10. P-13 glyph cache invalidation 全量 rebuild — 改为 lazy rebuild

P2（工程改进 — 中低短期 ROI）
 11. P-09 gaussian blur shader 朴素 textureLoad 优化 — 改用 texelLoad 近似
 12. P-10 blur dispatch workgroup size 2D tile — 1D workgroup 浪费调度槽
 13. P-14 per-glyph atlas upload memcpy 优化 — 逐行 memset 填充
 14. P-11 drop-shadow shader offset clamp — 修复越界读取风险
 15. B-01 提取核心库消除重复编译
 16. B-02 基准测试集成 CMake
 17. B-03 添加 filter 密集基准场景
 18. B-04 启用 GPU timestamp query
 19. B-05 增加细粒度 CPU 计数器
 20. B-06 Release 构建基准

P3（架构演进 — 长期收益）
 21. 全局 dirty-rect 跟踪覆盖到主渲染管线
 22. filter shader variant 编译时展开而非运行时 switch-case
 23. GPU 命令编码直接用 GPU buffer 而非 CPU 侧 command 流
 24. 多级 downsample pyramid blur 实现

七、积极发现

- ear-clip 已有 guard_max 上限，防止最坏情况无限循环
- clip dispatch 用 bucket 分组减少小 job 的 GPU 调度开销
- glyph cache hash 索引已实施，将查找从 O(n) 降到近似 O(1)
- T001~T009 已形成任务追踪体系，性能工作可量化管理
- 基准框架已有 p50/p95/mean 统计和 before/after 对比模板
- Effects 子系统纹理资源（ping_pong、shadow_composite）已持久化，
  避免了每帧重建
- Gaussian blur 分离式 H+V pass 设计合理，符合 separable convolution 规范

八、威胁模型（性能视角）

攻击者/场景              目标                     最可行性能退化向量
恶意网页               GPU DoS / 帧冻结       超长 filter chain（P-01 无上限）
恶意网页               CPU 帧抖动             频繁 clip_job + 堆分配（P-02）
内部回归               发布后帧时间退化       filter 系统无基准覆盖（B-03）
内部回归               开发迭代变慢           3× 重复编译（B-01）
资源受限设备           移动设备卡顿           全画布 4K blur + 多个 filter pass

十、队友补充发现（第二轮 — 已整合入报告）

本节收录 worker-core / worker-geom / worker-bench 在第一轮结论基础上的补充发现，
已按影响度并入对应章节，未重复内容以避免冗余。

十.一 worker-core 补充（核心渲染管线）

P-15 [HIGH] 无 ROI 的无条件全帧 CopyTextureToBuffer
文件: src/fullstack_core.c:4483, src/fullstack_core_canvas.c:151
补充: 即使业务层从未调用 getImageData，`fs_core_encode` 末尾也始终执行
       `fs_encode_canvas_readback_copy`，对整张目标纹理做整帧 copy。
       额外占用显存带宽，并为后续 CPU 读取埋下同步点。
       此问题与 P-05（readback poll）联动，属于同一代码路径的两层症状。
已并入: P-05 相关。

P-16 [MEDIUM] 无特效时渲染走 scene_texture → presentation 双 pass
文件: src/fullstack_core.c:4357-4478
补充: `effects_active == false` 时，渲染同样先落 scene_texture 再开
       presentation pass 复制到 target_view，而不是直接渲染到 target_view。
       增加了一次 render pass 切换、全屏三角形、一次纹理采样，
       以及 scene_texture 的额外读写。effects_active == true 时这套流程
       是必要的（filter chain 需要），但关掉滤镜时仍在付双 pass 代价。
优化方向: 在 `effects_active == false` 时直接渲染到 target_view，
         只有 filter chain 激活时才走 scene_texture 路径。

P-17 [MEDIUM] putImageData 路径额外分配 blit 临时缓冲
文件: src/fullstack_core.c:4748-4776
补充: `fs_core_put_image_data` 在将像素写入 canvas 时额外分配一次 blit
       临时缓冲，频繁调用时造成 CPU copy + 分配成本。
优化方向: 使用 frame-local scratch buffer 复用，或直接走 atlas upload 路径。

十.二 worker-geom 补充（几何与文字）

P-18 [MEDIUM] 文本 measure + draw 双遍
文件: src/fullstack_core_text_api.c:167, 561, 610, 263
补充: `fs_cmd_text_utf8_internal` 在 fs_text_align_offset / fs_text_baseline_offset
       时先完整 measure，再完整绘制。两遍都各自做 UTF-8 解码、image sequence
       匹配、fs_find_or_create_glyph、kerning 计算。长文本/动画文本时
       CPU 成本近似翻倍。
优化方向: 共享 layout 结果；无对齐/基线偏移时跳过预测量；
         shape/layout 路径一次性产出 metrics + glyph placements。

P-19 [MEDIUM] image sequence 匹配每个位置做全表线性扫描
文件: src/fullstack_core_text_glyph.c:273, 288, src/fullstack_core_text_api.c:268, 615
补充: `fs_find_image_sequence_match` 对每个文本位置遍历全部 image_font
       和 sequence 再逐个 decode 比较。emoji/贴图字形表大时每字触发高倍率扫描。
优化方向: 按首 codepoint 建索引桶；或为 canonicalized codepoint sequence
         建前缀树/状态机，把"每字扫全表"变成"首字符命中后小集合匹配"。

P-20 [MEDIUM] 带洞多边形 CPU 桥接 O(h^2) 排序
文件: src/fullstack_core.c:7270-7311, src/fullstack_core_paint.c:1081-1346
补充: 洞按 x 做冒泡式排序（O(h^2)）；每个洞 merge 重新分配 merged polygon；
       桥接点搜索/可见性检查扫描 outer；ear clipping 最终 O(n^2)。
       复杂路径/多洞 SVG 造成明显 CPU 拖慢。
优化方向: 洞排序改 qsort；预分配工作缓冲用链表/next-prev 索引替代 memmove；
         缓存 bridge 可见性候选；长期考虑将 fill 三角化迁到 GPU。

P-21 [MEDIUM] 曲线描边分段折线化命令膨胀
文件: src/fullstack_core.c:6684-6940
补充: quad/cubic 描边先按长度估 steps，再逐 step 求点；启用 dash 时每个小段
       再进 fs_emit_dashed_line_segment / fs_hit_dashed_segment_stroke，
       内部按 dash pattern 循环切分。复杂曲线 + 虚线从"每段曲线"退化
       成"steps × dash_segments × draw/hit-test"。
优化方向: 整条曲线先统一 flatten 成 stroke polyline，再在 polyline 上做 dash；
         round join/cap 命令化，减少 CPU 端逐小段发 draw command。

P-22 [MEDIUM] 动态着色 CPU 重复解析
文件: src/fullstack_core_text_api.c:216, 302, src/fullstack_core_paint.c:27, 148,
       src/fullstack_core.c:6742, 6792, 6854
补充: 文本每个 glyph 调用 fs_resolve_text_draw_color；stroke dynamic color
       对每个 join/segment/piece 重复 sample gradient/pattern。
       gradient stop 查找是线性扫描。CPU 端承担了本应 GPU 做的着色工作。
优化方向: 默认走 per-fragment shader 路径；CPU 侧仅传 paint 参数。
         必须 CPU 采样时缓存 gradient interval 和 atlas origin。

P-23 [MEDIUM] kerning 查询无 pair cache
文件: src/fullstack_core_text_api.c:370, 715, src/fullstack_core_text_glyph.c:697
补充: 非 shaping 路径每遇到相邻字形就调用 get_kerning_advance，
       长文本 measure + draw 双遍时放大 N 倍重复调用。
优化方向: 在 (font_slot, left, right, bake_px_q) 上加小型 pair cache；
         让 shaping/layout 一次性产出 advance 并缓存。

十.三 worker-bench 补充（基准与构建）

B-07 [HIGH] 归因计数器缺口 — 优化无法被定量验证
文件: Task/benchmarks/README.md:10-12, run_glfw_bench.ps1:120-180
补充: 当前基准只解析 queue_write/dispatch/draw/gpu_ticks 五个指标。
       T001（bind-group）、T002（render-pass）、T003（glyph lookup）、
       T005（join alloc）、T006（dirty-range upload）各自指向明确热点，
       但没有对应计数器映射。无法判断优化收益来自哪个子路径。
补充建议: 建立"场景指标 + 原因指标"双层 schema，至少补入：
         render_pass_begin_count、bind_group_create_count、
         glyph_cache_hit/miss/evict、stroke_join_alloc_count、
         triangulation_ms/verts、full_upload_frames/partial_upload_frames、
         readback_copy_count、cpu_preprocess_ms。

B-08 [HIGH] 构建配置不受控 — 基准结果可比性不足
文件: WCN/CMakeLists.txt:1-26, Task/benchmarks/run_glfw_bench.ps1:17-21, 104-108
补充: 原生 CMakeLists.txt 无默认 CMAKE_BUILD_TYPE，基准脚本不写 build type、
       compiler flags、git commit 到结果 JSON。同一脚本在空 build type、
       Debug、RelWithDebInfo、Release 下都跑出"合法但不可比"的数字。
补充建议: 基准脚本强制 RelWithDebInfo/Release；JSON 写入 CMAKE_BUILD_TYPE、
         generator、compiler id/version、compile flags、git commit、present mode。

B-09 [HIGH] 环境元数据缺失 — 复现依赖人工记忆
文件: Task/benchmarks/run_glfw_bench.ps1:1-4, Task/benchmarks/results/baseline-2026-02-24.json:2-5
补充: 脚本只有 Runs/ResultPath/PresentMode；JSON 只记 host 和 timestamp。
       无 GPU adapter、driver 版本、power mode、env flags、warmup 次数、
       frame budget、scenario seed。一次性抖动无法判断是驱动/资产变化
       还是代码变化。
补充建议: 脚本自动写入 commit、branch、GPU/driver、warmup、asset hash、
         实验特性开关（immediate mode、GPU round join gate 等）。

B-10 [MEDIUM] 场景矩阵未覆盖 fullstack 真实工作负载
文件: Task/benchmarks/run_glfw_bench.ps1:17-21, T009/T010/T008 task docs
补充: 当前只跑 path/text/image 三个 legacy demo。
       缺少 mixed UI/layout、text-layout、image+effects、small-batch/extreme-dirty、
       immediate-mode A/B 等 fullstack 场景。T009/T010/T008 文档要求
       的 profiler/verification 矩阵没有对应的基准面。
补充建议: 补 deterministic fullstack scenes；建立"任务 → 场景 → 计数器"对照表，
         让每个 Task 完成后有稳定验证面。
